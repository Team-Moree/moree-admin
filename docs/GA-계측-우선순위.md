# GA 계측 우선순위 (앱팀 요청서 / 기획 합의용)

> 목적: GA 대시보드가 "숫자 구경"이 아니라 **기획 의사결정 재료**가 되게 하려면 필요한
> 최소 계측을 정리한다. 순서는 **의사결정 → 필요한 이벤트/차원**으로 역산했다.
>
> 원칙: 절대수(vanity)가 아니라 **비율·퍼널·비교·변화**를 만들 수 있는 이벤트를 우선한다.
> 대부분의 인사이트는 아래 이벤트가 **앱에서 실제로 발화**되고 + GA4 **맞춤 측정기준 등록**이
> 되어야 나온다. (자동수집만으론 first_open·screen_view·retention 수준이 한계)

---

## 1. 인사이트 → 필요한 계측 (역산 표)

| 기획 의사결정(“그래서 뭘?”) | 인사이트 뷰 | 필요한 이벤트 | 필요한 파라미터 | 우선순위 |
|---|---|---|---|---|
| 온보딩 어디서 이탈? | 가입 전환 퍼널 (설치→가입→로그인) | `sign_up`, `login` | (없음, 카운트) | **P0** |
| 뭘 소싱/추가할지 | 검색 실패율 + 실패 검색어 | `search` | `search_term`, `has_result`(bool) | **P0** |
| 어떤 행사가 인기? 지역/유형별 관심 | 행사 조회 · 세그먼트 비교 | `view_item` | `item_id`, `item_name`, `event_type`, `location`, `status` | **P0** |
| 조회가 실제 행동으로? | 콘텐츠 전환율 (조회→북마크/공유) | `add_bookmark`, `store_share` | `item_id`, `method`(공유) | **P1** |
| 후기 작성률 | 리뷰 전환 | `review_submit` | `item_id`, `result` | **P1** |
| 어떤 유입·경험이 리텐션? | 세그먼트별 재방문율 | (자동 + 위 파라미터) | `platform`, `location`, `event_type` | **P1** |
| 화면별 이탈/체류 | 화면 흐름 | `screen_view` | `screen_name` | **P2** |

> 참고: 퍼널의 “단계별 인원”은 이벤트 카운트가 아니라 **사용자 단위**가 정확하다.
> GA4에서는 이벤트 필터 + `totalUsers` 또는 탐색(Exploration)의 유입경로/퍼널을 쓴다.
> 대시보드 MVP는 우선 이벤트 카운트 기준(참고용)으로 표시하고, 이후 사용자 기준으로 승격.

## 2. P0 — 지금 당장 붙여야 할 것 (전환/소싱/콘텐츠)

### 2-1. `sign_up` / `login`
- **발화 시점**: 회원가입 완료 / 로그인 완료
- **효과**: 설치→가입→로그인 퍼널, 가입 전환율. 온보딩 개선 근거.

### 2-2. `search` + `has_result`
- **파라미터**: `search_term`(문자열), `has_result`(true/false)
- **효과(최고 액셔너블)**: **검색 실패율**과 **실패 검색어 TOP** → “사용자가 찾는데 우리에게 없는 행사” = **콘텐츠 소싱 우선순위**.
- 주의(문서 5): API 실패는 로깅하지 않음. `has_result`는 결과 0건일 때 `false`.

### 2-3. `view_item` + 식별/세그먼트 파라미터
- **파라미터**: `item_id`, `item_name`, `event_type`(팝업/콜라보카페/전시), `location`(지역), `status`(오픈예정/진행중/종료)
- **효과**: 조회수 TOP 행사, 지역별·유형별·상태별 관심도.
- ⚠️ 서버 이슈(문서 비고 반영):
  - `event_type` — 서버가 안 내려줌(`category_type`은 다른 값). **클라에서 매핑 필요** 또는 서버 확장 협의.
  - `location` — 서버는 `lat/lon`으로 내려줌. 좌표 그대로 로깅은 PII/카디널리티 문제 → **지역 라벨(홍대/성수…)로 변환해서** 보낼 것. 원좌표 금지(문서 규칙).
  - 어떤 action에서 채워지는지(리스트 진입 vs 상세 진입) 정의 필요.

## 3. P1 — 콘텐츠 “먹히는지” 판단 (행동 전환)

| 이벤트 | 파라미터 | 인사이트 |
|---|---|---|
| `add_bookmark` | `item_id` | 조회 대비 북마크 전환율 (관심 강도) |
| `store_share` | `item_id`, `method`(kakao/link/instagram) | 조회 대비 공유 전환율 + 공유 수단 |
| `review_submit` | `item_id`, `result` | 후기 작성률 |

→ “이 팝업은 조회는 많은데 북마크 전환이 낮다” 같은 **콘텐츠 품질 시그널** 도출.

---

## 4. GA4 맞춤 측정기준 등록 목록 (event-scoped)

리포트에서 **파라미터로 쪼개 보려면** GA4 콘솔 → 관리 → 맞춤 정의 → 맞춤 측정기준에
등록해야 한다. **무료 티어 event-scoped 50개 상한** → 우선순위대로 등록.

| 우선 | 파라미터 | 범위 |
|---|---|---|
| P0 | `search_term`, `has_result` | event |
| P0 | `item_id`, `item_name`, `event_type`, `location`, `status` | event |
| P1 | `method`, `result` | event |
| P2 | `screen_name`, `element_name`, `position` | event |

## 5. QA / 검증

- **DebugView**: 기기 디버그 모드 + (권장) 별도 debug용 GA4 스트림/환경.
- 각 이벤트가 **이름·파라미터 키를 이 문서와 완전히 일치**시켜 발화되는지 확인(iOS/Android 동일).
- 등록 직후에는 GA4 리포트 반영에 지연(수 시간~1일) 가능 — 실시간은 DebugView로 확인.

---

## 6. 대시보드 연동 상태

- 대시보드(`/analytics`)에는 위 인사이트 패널이 **미리 만들어져** 있고, 계측+등록이 되면
  자동으로 채워진다. 현재는 **목업 토글**로 목표 화면을 미리 볼 수 있다.
- 붙는 즉시 확인 가능한 것부터(P0 `sign_up`/`login`/`search+has_result`) 순차 적용 권장.
